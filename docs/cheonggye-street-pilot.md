# 청계천 1×1km 자연스러운 거리 시범 (v3)

## 목표
실제 지도의 건물 윤곽·도로망·물길을 유지하면서 거리에서 이동할 때 자연스럽게 연결되는 환경을 만든다. 실측 높이의 복제가 목표가 아니다. DEM 잡음보다 도로 접속, 수면 연속, 건물 기초, 산책로 통행을 우선한다.

- 중심: 37.568149, 126.987684. 1,000×1,000m, 외곽 연결 160m.
- 제보 지점: 37.568297, 126.990929. 하천 양안 도로와 물길 간섭의 회귀 검사 위치.
- 게임/도시 뷰어/작업 스레드/비교 화면 모두 공통 MapCorrections 및 메시 생성 경로를 사용한다.
- 도시 뷰어: **청계천 1km 시범 구역**, **청계천 산책로 걷기**.
- `/tools/cheonggye-preview.html`: 상공·제보 위치·거리·산책로·다리 아래를 같은 구도로 비교.

## v1에서 교체한 부분
v1은 하나의 높이 격자에서 하천을 파고 도로 보호 마스크로 다시 올렸다. 수면까지 이 격자를 따라가고 산책로를 짧은 상자로 붙여 요철을 재현했다. 도로 중심선 검증만으로 수면의 오류를 발견하지 못했다.

v2에서는 그 하천 조각/상자 및 도로 마스크를 제거했다. 기존 하천 안의 담장은 렌더와 충돌 정보에서 함께 잘라내며, 대각선 담장의 넓은 충돌 박스가 산책로를 가로막지 않도록 짧은 구간으로 나눈다.

1. **육지**: 32m 격자 유지. 코어는 동쪽 -0.2%, 남쪽 +0.1%의 완만한 설계 경사로 정리하고 외곽에서 기존 지형에 연결한다. 경계 보간이 코어에 침범하지 않도록 32m 여유를 둔다.
2. **하천 경계**: OSM 중심선에서 단면을 만든다. 기존 지면 삼각형을 경계에서 실제로 잘라내어 하천 위에 지면이 남지 않는다. 도로 면도 같은 경계에서 잘라낸다.
3. **하천 단면**: 바닥·수면·하단 산책로·제방·상단 포장을 별도 면으로 생성한다. 수면은 횡단 방향 수평, 코어 종단 경사 0.15%로 연결된다. 인접 구간과 타일은 같은 경계 좌표를 공유한다. 실제 폭·수위의 실측 재현을 뜻하지 않는다.
4. **교량**: 물길을 건너는 도로의 연결 관계로 판별한다. 도로 상판, 하부 두께, 측면 난간을 만들고 아래의 물과 산책로를 유지한다. 기본 도로와 같은 재질·차선을 사용한다.
5. **진입**: 남쪽 제방 두 구간에 길이 100m의 완만한 왕복 경사로를 둔다. 중간 낮은 구간에서 하단 산책로로 들어갈 수 있다.
6. **건물**: 일반 건물의 노출 높이는 외곽 최대 접지 높이 기준으로 유지하고 하부를 기초로 채운다. 원본 건물 윤곽과 높이는 바꾸지 않는다.
7. **시설물**: 건물·차도·수역을 피한 공통 배치 후보를 이용해 가로수·벤치·가로등을 배치한다. 시범 구역의 기존 자동 소품과 중복을 제거한다. 가로등은 공통 도시별 야간 설정을 사용한다.
8. **재질**: 창문 음영/저층 마감과 도로 포장 외에 수변 석재 이음매, 산책로 포장, 약한 물결 표현을 추가한다. 별도 대형 이미지 파일은 없다.

## 이동과 렌더의 일치
`heightAt(x,z,feetY?)`는 발 높이를 전달하면 다리 위/아래를 구분한다. 발 높이를 생략하는 기존 스폰 등은 최상부 지지면을 선택한다. 플레이어 착지·경사 추종, 워커 발 접지, 카메라, 도시 보행이 이 경로를 사용한다. 하단의 이동자가 제방 벽에 닿았을 때 상단으로 순간 이동하지 않도록 제방 측면을 막는다. 교량 하부 천장과 난간의 완전한 입체 충돌은 아직 별도 과제다.

## 공통 구조와 범위
- `SurfacePartition.ts`: 속성을 보존하는 볼록 면 절단. 기존 지면/도로를 잘라 경계를 연결한다.
- `CheonggyePilot.ts`: 배치 레시피, 단면·높이·교량 판별·지지면.
- `CheonggyeRiver.ts`: 단면으로부터 연속 메시와 교량 생성, 수변 재질.
- `CheonggyeStreetDetails.ts`: 시설물만 담당. 하천 지형을 만들지 않는다.
- `cheonggye-pilot.json`의 `design`: 자연스러운 경사·폭·단차·경사로 위치. `plane`은 원본 DEM 추정 기록이며 기준 높이만 사용한다.

청계천 중심선이 동쪽으로 단조 증가한다는 조건에 맞춘 단면 생성기다. 다른 하천에 확대할 때는 굽이·분기·합류 및 교량 연결을 먼저 검증해야 하며 전 도시에 그대로 켜지 않는다. 외곽 연결 구간에는 기존 지형의 굴곡이 남을 수 있다. 가로수/벤치의 개별 충돌과 모든 출입구의 개별 모델은 아직 없다.

## 데이터·성능
서울 원본 지도와 Releases는 수정하지 않는다. 기존 2×2 압축 지도를 읽어 공통 생성 경로로 적용한다. 지형 표본을 청크당 66,049개에서 원래 1,089개로 되돌렸다. 좁은 하천만 경계 기반 삼각형으로 만들며 소품은 공간별 병합과 거리 숨김을 유지한다. FPS 개선량은 동일 조건의 별도 측정 없이는 주장하지 않는다.

## 검증
```sh
npx vitest run tests/cheonggyePilot.test.ts tests/cheonggyeSurfaces.test.ts tests/streetGeometry.test.ts tests/chunkMesh.test.ts tests/chunkPreparation.test.ts tests/PlayerController.test.ts
npm run build
```

검증은 도로 중심선만으로 끝내지 않는다. 실제 생성된 면에 광선을 쏘아 수면 횡단 수평·종단 연속, 기존 지면 제거, 교량 위/아래 높이, 경사로 접지 및 타일 경계 일치를 검사한다. 제보 지점도 포함한다.

현재 코어 내 하천 32m 밖 도로 8m 표본 3,256구간의 최대 경사는 약 0.224%, 하천 35m 밖 일반 건물 1,256개의 최대 접지 높이 폭은 약 0.243m다. 이 수치는 해당 표본의 기하 검증이며 실측 적합도나 모든 출입구 검사 결과가 아니다. 상세 결과는 `build/cheonggye-pilot-audit.json`에 생성된다.

레시피 재생성 및 검증은 `npm run build:city-surfaces -- seoul`. 원본 추출만 실행하려면 `python3 scripts/build-cheonggye-pilot.py`. 원본 지도 복원이 필요하다. 지도 배치와 설계 설정을 분리하여 원본을 다시 추출해도 v1 방식으로 되돌아가지 않도록 유지한다.


## 펜스·담장 접지 보강 (2026-09-26)
- `GroundedBarrier.ts`의 공통 생성기로 시범 타일의 일반/상세 담장을 만든다. 담장 폭 양쪽을 실제 지형 삼각형에서 절단한 뒤 입체 면으로 연결한다. 상부는 지면+담장 높이, 하부는 지면-6cm다. 전체 담장의 최저점까지 과도하게 연장하지 않는다.
- 상세 담장 위에 별도로 얹던 수평 박스 마감은 시범 타일에서 제거했다. 공통 입체 담장의 윗면이 마감까지 맡아 경사면에서 뜨거나 중복되지 않는다.
- 교량 난간은 3m 이하 간격의 입체 기둥과 연결 손잡이로 만든다. 기둥을 가장자리에서 20cm 안쪽에 두고 하천 바닥이 아닌 상판에 6cm 묻어 접지한다. 난간 자체의 충돌은 기존과 같이 아직 별도 과제다.
- 담장 충돌은 같은 지형 면에서 산출한 4m 이하 구간으로 만들고, 스레드 준비/복원 시에도 동일하게 유지한다.
- `tests/groundedBarrier.test.ts`는 굴곡/횡경사 합성 지형, 난간 기둥, 실제 4개 타일 담장, 실제 지형 메시와의 접지, 작업 스레드 왕복을 검사한다. 결과: `build/cheonggye-barrier-audit.json`.

### 지도 빌드 및 압축 전 검증 연결
`npm run audit:city-surfaces -- seoul`로 수동 실행할 수 있다. 동일 검증은 서울 원본 지도 빌드(`build-pipeline.mjs`, 서울 소스 ID는 `gyeongbokgung`)의 기본 검증 뒤, 그리고 서울 2×2 압축(`build-map-bundles.mjs seoul`)을 쓰기 전에 자동 실행한다. `maps:publish` 역시 이 압축 경로를 이용하므로 검사 실패 시 새 묶음 생성과 게시가 진행되지 않는다.

이번 변경은 **공통 접지 생성 로직과 자동 검증 연결**이다. 레시피 재생성은 아래 도로 보강 작업에서 빌드 단계로 연결했다. 레시피를 지도 묶음 안으로 옮기는 작업과 Releases 업로드는 아직 수행하지 않았다.


## 도로 연결 보강 및 재생성 단계 (2026-09-26)

### 원본과 설계의 구분
- 도로 위치·굽이·연결 관계는 기존 OSM 기반 지도에서 추출한다. 기존 타일의 폭은 대부분 `highway` 등급 기본값으로, **실측 폭이 아니다**. 차선/횡단보도 위치도 자동 배치 추정이다. `roadSource`에 이를 명시한다.
- `scripts/data/cheonggye-design.json`은 사람이 조정하는 설계 정본이다. 지면·수면 경사, 단면, 경사로, 도로 최소 폭과 제방 여유 폭을 여기에 저장한다. 원본 재추출 시 이 값을 초기화하지 않는다.
- `src/world/cities/cheonggye-pilot.json`은 생성물이다. 4개 원본 타일의 도로망을 주변 참조 범위까지 담아 타일 양쪽에서 같은 연결점과 차선 간격을 계산한다. 런타임에서 추출 작업을 다시 하지 않는다.
- 원본 지도/도로 보정/설계 파일의 SHA-256을 소스 감사 자료에 기록한다. 원본 높이와 맞지 않는 오래된 도로 보정은 런타임과 동일하게 적용하지 않는다. 하천 중심선이 현재 단면 생성기가 지원하지 않는 형태로 바뀌면 생성 단계에서 실패한다.

### 생성 규칙
1. `RoadNetwork.ts`는 렌더러에 의존하지 않는 순수 생성기다. 연결된 굽이의 도로 양쪽 가장자리 좌표를 공유하고 폭 차이는 구간 안에서 연결한다. 교차로와 급한 굽이·막다른 끝에만 둥근 마감을 사용한다. 짧은 구간의 안쪽 면이 뒤집히는 접합은 사용하지 않는다.
2. 차선 점선의 시작 거리는 연결된 도로 전체에서 누적한다. 교차로 앞 차선 비우기도 앞쪽의 짧은 선분들까지 전파하여 작은 선 조각이 교차로에 남지 않도록 한다.
3. 시범 구역 도로에는 폭에 맞춘 추정 차선 수를 사용한다. 넓은 도심 도로도 보도·연석·횡단보도 대상에 포함한다. 횡단보도는 하천 위와 다른 차도에 겹치는 접근부를 제외한다. 단, OSM 원본의 차선 수/일방통행 정보가 복원되기 전에는 실제 도색의 재현으로 보지 않는다.
4. `cheonggye_layout.py`가 남북 도로 사이 공간에서 하천 중심과 도로 배치를 함께 계산한다. 강변 도로는 설계 폭 8m를 유지하며, 하천 상단 경계와 차도 사이에 보도 여유 2.6m와 안전 여유 0.6m를 확보한다. 연결 도로도 같은 연속 변환을 적용하고, 바깥 160m에서 원본으로 복귀한다. 최대 도로 이동 허용값 12m를 넘으면 빌드를 중단한다. 현재 생성물의 최대 이동은 약 5.824m다.
5. 교량 상판과 지지면 판정은 같은 도로 외곽을 사용한다. 하부 산책로는 별도 지지면을 유지한다. 지상 도로의 높이는 기존 공통 지면과 일치시키며, 별도 덧댄 도로 높이로 지형 문제를 가리지 않는다.

### 맵 빌드 연결
```sh
npm run build:city-surfaces -- seoul  # 원본/설계 → 레시피 재생성 → 공통 형상 검사
npm run audit:city-surfaces -- seoul  # 재생성 없이 원본 일치 + 형상 검사
```
서울 `build-pipeline.mjs`는 원본 청크 생성/기본 검증 뒤 `buildCitySurfaces`를 실행한다. 2×2 압축은 원본/설계와 레시피의 일치 여부 및 형상 검증을 먼저 확인한다. 오래된 레시피가 감지되면 압축을 중단하고 위 재생성 명령을 안내한다. 도로·하천·담장 검증은 동일한 게임/뷰어 생성 코드를 실행한다.

이번에는 이 시범 구역 생성 단계만 실행했다. 서울 전체 OSM 재수집, 전체 맵 재빌드, 2×2 재압축, Releases 게시는 수행하지 않았다. 현재 레시피는 앱에 포함된다. 향후 지도 묶음으로 이관할 때는 원본/설계/생성 레시피 버전을 함께 묶고 공통 생성기와 호환성을 확인해야 한다.

### 도로 검증
`tests/roadNetwork.test.ts`는 굽이 접합/중복 선분/실제 T 교차로 보존, 실제 시범 구역 도로의 면 뒤집힘, 연결점 일치, 생성 노면의 높이와 경사를 검사한다. 노면 중심과 좌우 50%·98% 폭 위치에서 실제 노면 삼각형의 수직 교차 높이를 검사한다. 하천 안에 들어간 일반 도로를 검사에서 제외하지 않고 실패시킨다. 결과는 `build/cheonggye-road-audit.json`이다. 주변 경계 연결부와 원본 폭/일방통행 태그 정확도는 별도 검토 대상이다.

## 차선 빌드 단계 (2026-09-26)

`build:city-surfaces -- seoul`은 이제 원본/설계 → 도로·하천 레시피 → **차선 배치 생성** → 형상 검증 순서로 실행한다.

- `RoadMarkings.ts`: 도시/렌더러에 종속되지 않는 연결 도로 단위 차선 생성기. 단면이나 청크마다 점선 간격을 초기화하지 않는다.
- `scripts/build-road-markings.mjs`: 확정된 도로망과 하천 경계에 공통 생성기를 실행한다. `cheonggye-markings.json`에 도로 키와 도색 구간을 간결한 수치 배열로 기록한다.
- 게임·뷰어·작업 스레드의 `StreetGeometry.ts`가 같은 생성물을 사용한다. 시범 구역에서는 실행 중에 교차로/횡단보도를 다시 추정하지 않는다.
- 차선 설정은 `scripts/data/cheonggye-design.json`의 `markings`에 저장한다. 현재 선 폭 24cm, 점선 4m/주기 11m. 추정 배치이며 실제 일방통행·차선 수·도로 도색을 측량해 복제한 것은 아니다.

### 자연스러운 연결 규칙
1. 굽이와 폭 변화 지점에서 같은 미터 단위 간격으로 차선을 연결한다. 도로 폭이 변해도 도색 폭이나 차선 위치가 단면 경계에서 튀지 않는다.
2. 중앙선·점선은 연결 도로 전체에서 생성한 뒤 렌더용 조각으로 나눈다. 2m 미만으로 남은 점선과 6m 미만의 고립된 실선 구간을 제거한다. 정상적인 긴 선을 청크 경계에서 나눈 작은 삼각형은 제거하지 않는다.
3. 교차로는 다른 도로의 실제 외곽까지 고려해 비운다. 얕은 각도로 교차하거나 겹치는 도로도 포함한다. 가까운 접속부 간격이 `max(mergeGap, 도로 폭×1.2)` 이하면 하나의 교차로로 취급해 다리 가운데 짧은 차선 섬이 남지 않게 한다.
4. 횡단보도는 도로 조각의 길이가 아니라 합쳐진 교차로의 접근부에서 생성한다. 하천, 다른 차도와 겹치는 후보는 만들지 않는다. 정지선은 진입 방향의 차로에만 둔다.
5. 차선 계획은 최종 노면 높이와 공통 지면 절단을 사용한다. 별도로 노면을 올리거나 깊이 검사를 끄는 방식으로 오류를 가리지 않는다.

### 자동 검증과 적용 범위
`tests/roadMarkings.test.ts`가 도로 분할 전후 동일성, 점선 간격, 얕은 교차, 넓은 교량의 연속 교차로, 폭 변화 접합, 빌드 생성물 재현 및 하천 침범을 검증한다. 차선 배치 JSON은 약 361KB, gzip 기준 약 69KB다. 현재 차선 생성물은 1,535개 도로 조각/9,522개 도색 조각이며, 지지면 표본 57,132곳을 검사한다. 결과는 `build/cheonggye-marking-audit.json`에 남는다.

지도 빌드와 압축 전 검사에 차선 검사도 포함된다. 원본 레시피·도로/차선 생성기·빌드 스크립트 해시 또는 생성 결과가 달라지면 오래된 차선 데이터로 압축할 수 없다. 이 적용은 청계천 시범 구역이며 다른 도시의 도색은 아직 전환하지 않았다. 레시피는 앱에 포함되고 Releases는 재게시하지 않았다. 향후 도시별 도로 규칙(좌측통행/일방통행/차선 수)이 확보되면 같은 생성기에 입력으로 추가한다.

청계천의 일정 단면/옹벽/양안 도로 설계는 이 시범구역 전용이다. 다른 도시 하천의 분류와 원형 보존, 교량 태그, 타일 연결 검증은 [공통 하천 맵 빌드 규칙](river-map-build.md)을 따른다.


## 도로 색상·질감 공통화 (2026-09-26)

시범 사각형 안에만 어두운 아스팔트/보도 색을 섞던 `realismArea` 및 위치 기반 셰이더 덧칠을 제거했다. 청계천 내부의 최종 선형 색 혼합 결과를 sRGB로 환산해 서울 공통 프로필(`paintedSeoul.street`)에 저장했다. 아스팔트 `#535c60`, 보도 `#c2bdb0`이며 같은 서울 프로필을 쓰는 모든 일반 도로/교량에 적용한다. 다른 도시의 팔레트는 해당 도시 프로필을 따른다.

`StreetMaterialDetail.ts`가 아스팔트 입자·보도 줄눈·마모의 공통 미터 단위 셰이더를 제공한다. `StreetGeometry`(일반 도로, 교량, Worker 준비 메시)와 `StreetSurface`(텍스처 방식 지면 도로)가 함께 사용한다. 좌표·시범 구역 여부에 따른 별도 색상 처리가 없다. 원거리 미세 패턴은 픽셀 크기에 맞춰 약해진다.

색상/질감은 지도 원본이나 2×2 압축에 구워 넣는 값이 아니라 앱의 도시 프로필과 렌더러 설정이다. 따라서 이 변경은 재압축 없이 기존·신규 지도 모두에 적용된다. 일반 지도 빌드/압축의 `validateCitySurfaces`에 `streetAppearance.test.ts`를 추가하여 서울 기준 색 보존, 도시별 팔레트, 일반/시범/교량/준비 메시/텍스처 경로의 일치를 검사한다. 청계천 비교 페이지도 양쪽에 같은 도시 재질을 사용한다.

이번 공통화 대상은 **도로·보도 색상과 표면 질감**이다. 청계천 전용 하천 단면·옹벽 및 도로망/차선 배치의 적용 범위는 위 절의 설명대로 구분한다. 모든 시범 설계가 모든 도시로 복제된 것은 아니다.


## 평행 도로의 차선 누락 보정 (2026-09-26)

37.570273, 126.987768 서쪽 진입 도로의 차선 누락은 추정 폭이 겹친 평행 도로를 교차로로 간주하여 장거리 도색을 제거한 것이 원인이었다. 도로 폭 전체가 겹쳤다는 이유만으로 교차부로 처리하지 않는다.

- 공통 `RoadNetwork.roadJunctionCandidate`가 평행/거의 평행한 도로는 중심선의 실제 교차 여부를 확인하고, 거의 직진하는 공유 끝점은 연속 도로로 구분한다. 실제 얕은 각도 교차는 계속 비운다.
- 지도 차선 생성기 `RoadMarkings`와 일반 도로 렌더러 `StreetGeometry`가 같은 후보 판정을 사용한다. 특정 위경도 조건을 보정 코드에 넣지 않았다.
- 추정 폭이 겹친 평행 차도는 겹친 구간에서 긴 연결 도로를 우선하여 차선을 한 번만 그린다. 연결 길이가 같으면 공간 범위로 결정하며 입력 순서/분할 조각 수와 무관하다. 차선 소유권이 바뀌는 곳에 횡단보도를 만들지 않는다.
- 공통 단위 검사 `roadMarkingRules.test.ts`는 지도 도시와 무관하게 매 빌드/압축에서 실행된다. 평행한 분리 차도, 8~10m 조각 분할, 실제 얕은 교차, 넓은 교량 진입부, 폭 변화, 점선 위상을 검사한다. 제보 좌표는 서울 회귀 검사에만 들어간다.
- 청계천 생성물을 다시 만들어 1,520개 도로 조각에 10,389개 도색 조각을 생성했다. 횡단보도 5,117조각은 그대로이며 검사한 지지면 표본은 62,334개다. 교차로 가운데까지 억지로 차선을 그리는 수정은 아니다.

차선 레시피는 앱 소스에 포함되므로 이번 변경에 지도 압축/Release 재게시가 필요하지 않다. 기존 지도 및 향후 공통 빌드·렌더링 경로에서 같은 판정을 사용한다. 도로 폭은 여전히 OSM 도로 등급에 따른 추정이 포함되므로 실제 일방통행/차선 수를 복원한 것은 아니다.


## 중앙선만 표시하는 공통 도로 표현 (2026-09-26)

시각적으로 자연스러운 결과를 우선한다. 실제 차로 수를 추정해 복잡한 도색을 늘리지 않는다. 흰 점선·횡단보도·정지선은 생성하지 않고 노란 중앙선만 남긴다. 폭과 관계없이 단일 중앙선을 쓰며 폭 6m 미만은 생략한다.

- `RoadMarkings.planRoadMarkings`는 지도 빌드용 생성물, 모든 도시의 일반 도로 메시, 원거리 지면 텍스처가 사용하는 하나의 중앙선 계획기다. 청계천 전용 판정이나 좌표 예외를 추가하지 않는다. 게임/도시 뷰어/Worker 메시 준비도 이 경로를 공유한다.
- 교차로 여백, 겹친 평행 도로의 중복 억제, 연결 도로 단위의 최소 선 길이, 접합부 정렬을 유지한다. 지도 원본의 작은 분할 조각마다 선을 재시작하지 않는다. 교량도 공통 중앙선 폭·간격 규칙을 쓴다.
- 일반 지도 빌드·압축의 `validateCitySurfaces`에서 중앙선 생성 규칙과 실제 도로/교량/텍스처/Worker 준비 경로를 검사한다. 차선 조각이 접히거나 교차로를 가로지르는지를 검사하며, 흰 도색이 다시 생기면 검증에서 실패한다.
- 기존 흰 차선·횡단보도 관련 절은 과거 상태이며 이 정책으로 대체한다. 청계천 생성물도 다시 생성한다. 도색 생성물은 앱 소스에 있고 일반 도로는 원본 도로망으로 공통 계획기를 실행하므로 이번 변경 때문에 원본 지도/2×2 번들 또는 Releases를 다시 게시할 필요는 없다.

이 변경으로 모든 도시의 도로 원본 품질까지 검증됐다는 뜻은 아니다. 일반 도로 계획에는 로드된 도로 범위, 청계천 생성물에는 전체 설계 도로망이 입력되며 타일 경계의 이웃 도로 데이터가 없는 경우까지 원본 연결을 복원하지는 않는다. 새 보정은 공통 계획기에 넣고 도시별 좌표 예외 대신 재현 가능한 입력 도로망으로 검증한다.

중앙선 통합 후속 보정은 [공통 도로 보정 기준](road-grade-repair.md)의 겹친 양방향 도로 절을 따른다. 현재 생성물은 1,358개 도로 조각 / 2,013개 도색 조각이며 시작·끝 오프셋을 각각 저장한다.
