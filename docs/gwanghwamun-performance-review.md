## 확인한 구조
- StreamingWorld 게임 설정은 반경 2600m, 유지 여유 600m, 캐시 48개, 모든 고도에서 상세 청크를 사용한다. 도시 뷰어에만 최근 반경 1200m/캐시 0개가 적용되어 있다.
- ChunkStreamer.toCache는 핸들을 캐시 Map으로 옮길 뿐 장면에서 숨기거나 분리하는 훅이 없다. StreamingWorld의 그룹/충돌/전투 등록 해제는 캐시 최종 폐기 시점에만 실행된다. 시야 밖 메시의 프러스텀 컬링은 작동할 수 있으므로 모두 매 프레임 그려진다는 뜻은 아니지만, 장면 순회 및 메모리와 검색 대상에는 남는다.
- drainBuilds의 8ms 예산은 한 번 시작한 build를 중단하지 못한다. buildChunkMesh는 도로/건물/나무 병합을 동기 실행한다. 단순 예산 축소로 한 청크의 긴 정지는 해결되지 않는다.
- StreetGeometry는 도로를 여러 표면층으로 만들고 지형 삼각형마다 잘라낸다. 연석은 약 1.5m마다 분할한다. 드로우콜을 병합했어도 정점 수와 생성 비용이 크다.
- 청크 변경 시 StreamingWorld.rebuildCollision은 objReg 전체의 충돌 구조를 재생성한다. 캐시된 지역도 최종 폐기 전까지 objReg에 남는다.
- 건물은 청크 단위로 병합되어 있어 개별 건물 하나당 드로우콜을 내는 구조는 아니다. 반면 시야 일부에 걸친 큰 청크는 넓은 범위의 건물 정점을 제출할 수 있다.
- 게임 그림자는 2048x2048 PCFSoftShadowMap을 사용하고 태양 그림자 카메라가 플레이어를 따라간다. 도시 뷰어에서는 shadowMap을 활성화하지 않는다. 두 화면의 성능을 직접 동일시하면 안 된다.
- 미니맵은 queryMinimap으로 등록된 도로/수역 전체를 순회한 뒤 거리 판정한다. 이 비용과 그림자/GPU 비용의 비중은 실제 브라우저 계측이 필요하다.

## 권장 적용 순서
1. 캐시 상태와 활성 상태를 분리한다. 캐시 진입 시 렌더 장면/충돌/전투 검색에서 제외하고 복귀 시 재등록한다. 파괴 이력 보존 및 재진입 회귀 검증을 동반한다.
2. 도로 메시를 미리 생성해 저장하거나 Worker에서 생성한다. 전송 가능한 typed array로 결과를 전달하고 GPU 업로드는 프레임별로 나눈다. 멀리 있는 연석/노면 층을 단순화한다.
3. 거리 기반 상세도(LOD)를 적용한다. 가까운 도로/랜드마크 외형은 유지하고 원경 건물 부속물과 수목을 단순화한다. 고도가 높아졌다고 주변 건물 전체를 제거하지 않는다.
4. 충돌은 변경 청크 단위로 갱신하고, 미니맵은 인접 청크만 조회/정적 배경 캐시를 활용한다.
5. 실제 비행에서 그림자와 화면 해상도를 따로 비교한 뒤 필요한 경우에만 동적 품질을 적용한다.

검증 시 같은 경로·고도·화면 크기에서 최초 진입, 정지, 이동, 재방문을 분리하고 프레임 시간 p50/p95/p99, 최장 정지, 생성 시간, GPU 시간(지원 시), 제출 삼각형/드로우콜, 활성/캐시 청크 수를 기록한다.


## 1차 최적화 적용
- 캐시 진입/복귀 훅을 추가했다. 캐시 그룹은 장면에서 분리하고 지형/충돌 원본 목록 및 전투 표적 조회에서 제외한다. 복귀 시 기존 건물 HP와 붕괴 진행 상태를 유지한다. 게임 캐시는 48개에서 4개로 제한했다.
- 도로 생성과 법선 계산을 월드별 Worker로 옮겼다. 기존 bounded fetch 대기열 안에서 처리하고 위치/법선/노면 좌표 배열을 transferable로 전달한다. 메인 스레드는 배열을 복사하지 않고 메시 속성에 연결한다. 월드 종료 시 Worker와 대기 작업을 종료한다. Worker 미지원 환경은 기존 동기 경로를 사용한다.
- 청크 도로 바운딩 박스까지의 수평 거리를 기준으로 먼 차선/중앙선/연석을 숨긴다(850m 밖, 복귀 700m 이내). 아스팔트, 보도, 건물은 유지한다. 건물과 수목의 별도 단순 모델 LOD는 아직 적용하지 않았다.
- 별도 Worker URL을 Vite가 정상 치환하도록 해당 로더 파일만 난독화 대상에서 제외했다.
- 전체 테스트 1780개 및 추가 Worker 수명주기 테스트 1개 통과. 타입 검사/배포 빌드 통과. 도시 뷰어의 도로·건물 표시와 오류 로그 확인 완료.
- 실제 게임 비행 FPS 전후 비교는 아직 하지 않았다. 건물/지형 생성 및 전체 충돌 재구축은 여전히 메인 스레드에 있으므로 남은 끊김은 추가 계측 대상이다. 캐시된 파괴 잔해는 기존 공용 잔해 메시 구조를 유지한다.


## 2차: 선준비와 활성화 분리 / 공통 계측

- 게임과 도시 뷰어는 같은 `STREAM_CFG`를 사용한다. 원래 보이는 반경 2,600m와 추가 선준비 반경 3,624m를 구분했다.
- 활성화는 플레이어와 타일의 사각 경계 사이 최단거리로 판정한다. 타일 중심만 기준으로 잘라 시야 경계의 지형이 사라지는 문제를 피한다. 활성 타일에는 128m 복귀 여유를 둔다.
- 선준비 타일은 데이터를 읽고 도로 Worker 및 건물 메시 생성까지 수행하되, 장면·충돌·전투 표적에서 제외한다. 접근하면 재다운로드/재생성 없이 활성화하고 파괴 상태를 보존한다. 준비 영역을 완전히 벗어난 타일만 기존 4개 LRU 캐시 정책을 적용한다.
- 실제 현재 위치의 활성 범위를 예측 선로딩보다 우선 처리한다. 속도가 빨라도 현재 화면에 필요한 타일이 후순위로 밀리지 않게 한다.
- `RenderMetrics`는 두 화면에서 동일하게 최근 5초 FPS/p95, CPU 프레임 시간, 전체 렌더 패스의 제출 삼각형·그리기 호출, 활성/선준비/캐시/대기 수와 타일 생성·충돌 갱신 최대 시간을 표시한다. GPU 실행 시간을 측정한 값은 아니다. 숨겨진 탭의 측정 구간은 초기화한다.
- 도시 뷰어는 오른쪽 패널에 항상 표시하고 게임은 기존 `?diag` 진단 모드에서 표시한다. 여러 렌더 패스의 카운터를 합산하며 뷰어 종료 시 렌더러 카운터 설정을 복원한다.
- 회귀 테스트는 선준비 타일의 비활성 생성, 접근 활성화, 동일 핸들 재사용, 후퇴 비활성화, 빠른 전방 예측에서도 현재 위치 범위 유지 및 기존 캐시/파괴 상태 경로를 검사한다.

이 단계는 멀리 준비된 메시의 상시 렌더·충돌 부담을 줄이는 변경이다. 원거리 건물 LOD, 건물 생성의 Worker 이동, GPU 업로드 분할, 충돌 구조의 청크별 증분 갱신은 아직 구현하지 않았다. 초기 로딩 최대값은 순수 정상 상태 FPS와 구별해야 하며, 빌드/테스트 동시 실행 시 측정 수치는 성능 비교 근거로 사용하지 않는다.


검증: 관련 26개 테스트 및 타입 검사 통과, 배포 빌드 통과(기존 번들 크기/난독화 소스맵 경고 유지). 기존 탭은 반복 개발 재로딩 후 Array buffer allocation failed 오류로 재진입에 실패했으나, 새 탭에서는 같은 서울 좌표 37.578000,126.977000 / 높이 141m에서 정상 로딩을 확인했다. 새 탭의 단일 표시 구간은 활성 32 / 선준비 7 / 대기 0, 약 54.4 FPS, p95 27.9ms, 제출 삼각형 1,379,258 / 117회였다. 타일 생성 최대 550.5ms, 충돌 갱신 최대 30.7ms가 남아 있다. 동일 조건 이전 버전 FPS를 재측정하지 않았으므로 개선율은 주장하지 않는다. 장시간 이동·재방문 및 기존 탭 메모리 오류의 원인 분리는 추가 검증 대상이다.


### 야간 창문 가시거리 통일
건물 종류별 창문 간격(일반 3.1m, 오피스 1.7m)이 같은 화면 미분 기반 detail 감쇠에 들어가 고층 오피스 창문 발광이 더 가까운 거리에서 사라졌다. 야간 발광용 nightGlazing을 낮의 창문 재질과 분리하고, 모든 종류에서 일반 저층 기준 3.1m × 3.2m 공간 척도로 가시성을 계산한다. 해상도 이하로 작아진 촘촘한 창문은 평균 창 면적 비율로 부드럽게 전환해 밝기가 갑자기 소실되지 않게 한다. 화면 해상도·관측 각도·안개에 따른 감쇠는 유지하며 고정 미터 거리에서 켜지는 스위치는 아니다. 게임과 도시 뷰어의 공통 외벽 셰이더에 적용한다.


## 3차 검토: 도시 뷰어 Shift 공중 이동

### 이번 확인 범위
2026-09-13 실행 중인 도시 뷰어의 공개 성능 패널과 현재 코드를 확인했다. 자동 입력으로 동일 경로의 Shift 유무를 통제한 A/B 측정은 하지 않았다. 현재 위치는 37.564579, 126.967228, 높이 262.4m였다. 패널의 두 표본은 43.9/52.0 FPS, p95 66.1/50.6ms, 제출 삼각형 1,436,682, 그리기 98회, 활성 33/선준비 16/캐시 4/대기 0이었다. 타일 생성 최대 2191.1ms, 충돌 재구축 최대 147.1ms는 현재 월드의 누적 최대값으로 초기 로딩을 포함한다. CPU 표시 3.5/5.8ms는 표시 시점 프레임 값이며 CPU 병목을 배제하는 평균값이 아니다. GPU 시간과 서버 지연은 측정하지 않았다.

### 원인과 우선순위
1. **한 청크의 동기 생성 중단 불가**: ChunkStreamer의 8ms 예산은 다음 청크를 시작할지만 결정한다. 한 청크의 지형 배열/법선, 표면 텍스처 베이크, 건물 압출·장식·병합, 전투 등록은 메인 스레드에서 끝까지 실행한다. 2191ms 생성 표본은 이 경로가 프레임을 장시간 점유할 수 있음을 보여준다. 도로만 현재 Worker 처리다. 건물·지형 순수 배열 생성을 Worker로 옮기고, 텍스처는 사전 생성 또는 지원되는 별도 작업으로 분리한다. 메인 스레드의 메시 연결·등록은 작은 묶음으로 나눠 프레임당 2~4ms 목표로 처리한다. GPU 업로드는 별도 측정/분산 대상이다.
2. **충돌 전체 재구축**: 타일 활성 집합 변화마다 objReg 전체의 건물·벽을 재등록하고 finalize한다. 청크별 공간 인덱스를 유지하고 변경 청크만 추가/삭제한다. 게임의 건물 파괴 상태와 발밑 지형, 타일 경계 충돌 회귀 검증이 필요하다. 도시 공중 모드만 충돌을 끄는 임시 분기를 만들지 않고 공통 월드에서 해결한다.
3. **이동 중 선준비 부하/우선순위**: 일반 48m/s 대비 Shift 320m/s는 약 6.67배다. 격자 한 변 1024m를 직선 이동하는 데 이상적으로 21.3초에서 3.2초로 줄어든다(이는 타일 1개 로딩 간격이 아니다). 반경 3624m 창 전체의 앞쪽 가장자리에는 여러 신규 타일이 들어온다. 활성 반경 2600m와 추가 준비 링은 유지하되, fetch/도로 준비/건물 생성/장면 등록을 개별 큐로 분리한다. 위치·방향 변화에 맞춰 대기 작업 우선순위를 재계산하고 불필요한 준비 작업을 취소한다. 현 구조는 필요 없어진 결과를 나중에 버릴 뿐 진행 중 fetch/도로 Worker 작업을 취소하지 않는다. 속도 예측은 현재 위치 변화 및 실제 경과 시간과 일치하는지도 회귀 검증한다.
4. **정상 상태 렌더링 비용**: 대기 0에서도 약 144만 삼각형이 제출된다. 건물/수목/랜드마크 부속물 거리 LOD와 병합 메시의 더 작은 공간 묶음으로 시야 밖 정점 제출을 줄인다. 상세도를 전환할 때 창문 밝기·실루엣이 튀지 않도록 한다. 병합을 무조건 잘게 나누면 드로우콜 증가하므로 측정으로 크기를 정한다.
5. **반복 방문·서버·GPU 분리**: 기존 캐시는 4개로 제한되어 재방문 재생성이 생길 수 있다. 개수만 늘리지 말고 버퍼 바이트 예산과 원본/생성물 캐시를 분리한다. JSON 파싱/도시 보정은 buildMs 외부의 메인 스레드 작업이므로 별도 계측한다. 개발 서버 요청 대기와 GPU 업로드/그리기 시간도 구분해서 기록한다. 현재 자료만으로 서버 또는 GPU를 주원인이라 단정하지 않는다.

### 권장 실행 및 합격 기준
먼저 생성 단계별 시간, 최근 5초 최대/긴 프레임 수, 활성화·업로드 시간을 추가 계측하면서 1번을 적용하고, 다음 2번, 3번, 4번 순서로 진행한다. 이동 속도와 사전 준비 범위는 유지한다. GPU 병목 확인 전에는 해상도나 전체 외형 품질부터 낮추지 않는다.

동일 위치·시선·고도·화면 크기에서 초기 로딩, 정지, 일반 이동, Shift 이동, 역방향 재방문을 분리한다. 새 지역과 캐시 재방문을 각각 측정하고, 최소 3회 반복해 FPS/p95/p99/최장 프레임, 생성 단계 시간, GPU 시간(지원 시), 대기/활성 수, 메모리, 지형 누락을 비교한다. 목표는 단일 메인 스레드 작업을 4ms 내 작은 묶음으로 분할하고, 테스트 기기에서 Shift 구간 p95 33ms 이하·100ms 초과 정지 제거를 지향하는 것이다. 달성 수치가 아닌 검증 목표다.

이번 요청에서는 검토 문서만 추가했으며 런타임 속도·렌더링 설정은 변경하지 않았다.


## 3차 구현 결과: 타일 생성 분리와 증분 활성화

- 게임/도시 뷰어 공통 StreamingWorld에 단일 ChunkPreparation Worker를 연결했다. 타일/보정 JSON 읽기·파싱, 기존 공통 빌더의 건물/지형/수목/랜드마크 계산, OffscreenCanvas 지형 표면 그리기, 도로 생성, 충돌 형상 추출을 별도 작업에서 수행한다. 정점 배열과 지형 이미지는 transferable로 전달한다. Worker가 배포 assets 폴더 안에 있어도 페이지 기준 지도 URL을 사용한다.
- 메인 스레드는 기존 재질/창문/야간/노면 셰이더를 복원하고 메시 단위와 건물 전투 등록 32개 단위로 양보하는 iterator를 진행한다. 프레임당 조립 예산은 4ms이며 하나의 단계가 넘을 수 있는 협력형 예산이다. GPU 업로드 자체를 비동기 완료 보장하는 것은 아니다. OffscreenCanvas/Worker 미지원 환경은 기존 동기 공통 빌더를 사용한다.
- 충돌 공간 인덱스는 청크별로 생성·보관하고 활성화/비활성화 때 붙이거나 뗀다. 인접 청크 전체 재구축을 제거했다. 캐시 복귀 시 기존 콜라이더 상태를 재사용하고 파괴 이력을 재적용한다. 발밑 지형, 빔 차폐, 미니맵, 파괴/복구는 기존 공통 충돌 질의를 사용한다.
- 대기 작업 우선순위를 현재 위치/방향으로 갱신한다. 불필요해진 대기 작업은 제거하며 이미 실행 중인 불필요한 Worker 작업은 종료 후 필요한 작업으로 재시작한다. 부분 조립 취소 시 메시/재질/이미지와 전투 등록을 해제한다. 준비·대기 합계 상한 6개와 캐시 4개, 활성 2600m/선준비 3624m, 이동 48/320m/s를 유지했다.
- 건물은 256m 구역별 그리기 범위와 경계로 분리해 시야 밖 제출을 줄였다. 모든 구역은 원본 정점 속성을 공유하므로 복제 VRAM 없이 기존 파괴 정점 갱신이 반영된다. 더 작은 구역은 그리기 호출 수를 증가시킬 수 있으므로 만능 LOD로 취급하지 않는다. 멀리 있는 가로등 몸체/나무 줄기는 1200m에서 생략, 1050m 안에서 복귀한다. 수관과 야간 등불, 건물 실루엣은 유지한다. 건물 자체의 저정밀 대체 모델은 추가하지 않았다.
- 성능 패널에 별도 생성/활성화 최대 시간을 추가했다. `?stream-review=1#city` 에서만 일반/고속 20초 동쪽 이동 측정을 제공하며 동일 입력·이동·월드 갱신 경로를 이용한다. 수동 키/드래그나 포커스 이탈 시 중단한다.

### 실행 중 검증
- 전체 118개 테스트 파일의 1803개 테스트 통과(초기 핵심 변경 기준). 이후 원거리 소품 및 Worker 지도 기준 URL 검증을 포함한 관련 36개 테스트도 통과했다.
